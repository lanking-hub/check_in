# 智慧签到墙 · 需求范围 v1

> 状态：待与原型图对齐。数据层（本机 / 服务器）本次不定，接口先抽象，后端接入时替换实现。
> 截止：11 月 9 日展示。学校：新城附小。方案名（孙博简化版）：汇聚星光 · 点亮乐学。

## 0. 边界：做什么 / 不做什么

**我们做（本次）**
1. 大屏展示二维码，参观者手机扫码
2. 手机端填写信息并手写签名
3. 签名在 1～2 秒内实时出现在大屏签到墙上（项目的"魔法时刻"）
4. 手机端生成入校电子身份牌，可保存 PNG

**不做（明确排除）**
- 导览平台：归其他项目 / 学校已有导览矩阵，不在本任务范围内
- 空间定位与自动感应：群里已确认砍掉
- 语音智能体、打捞船、机械手等其他 6 项：其他负责人
- 后台管理端、账号体系、数据导出：本次不做，除非孙博要求

**数据层**：已定 —— 走公网服务器。大屏是 Windows 一体机，用浏览器打开公网地址；访客手机用移动网络扫码访问同一地址，不需要连校园内网。前端统一走 `Store`（读写）和 `Bus`（推送）两个接口，开发期用本机方案占位，接入服务端时只替换适配器，页面代码不动。

## 1. 大屏端（大厅电视 / 平板 / 一体机）

### 1.1 能力清单

| 编号 | 能力 | 说明 |
|---|---|---|
| A1 | 二维码入口 | 展示签到二维码；同时给出文字地址兜底；断网时有占位图案，不能出现空白方块 |
| A2 | 签到墙 | 接收签名并以动画呈现，逐步垒高；容量目标 ≥ 100 条，不卡顿、不重叠 |
| A3 | 实时数据 | 今日到访、已签到、当前在线（口径待定）、最近签到者 |
| A4 | 理念呈现 | 口号 + 视觉符号（沙粒 / 星光），不放大段文字 |
| A5 | 现场运维 | 一键清空、模拟数据（彩排用）、断线提示、长时间常亮不睡屏 |

### 1.2 交互
- **只读展示，无触摸操作**，全部由手机端驱动；不依赖现场有人操作大屏
- 新签名到达：0.5 秒内启动动画，1～2 秒完成落位
- 数字变化用缓动计数，柔和过渡，不闪烁、不跳动
- 自适应 16:9 横屏与 9:16 竖屏一体机两种形态
- 断线时保留已显示内容，并在角落给出提示，不清空签到墙

### 1.3 样式
- 三个候选视觉版本待选：**沙粒版**（沙色＋暖金＋青绿，"乐学，从一粒沙开始"）、**星光版**（夜空＋金色星点，"汇聚星光 · 点亮乐学"）、**极简版**（白底细线）
- 远距离可读性：标题 ≥ 30px，统计数字 ≥ 34px，等宽数字避免抖动
- 动效克制，100 个元素内保持流畅，不做炫技特效

## 2. 手机端（参观者自带手机）

### 2.1 能力清单

| 编号 | 能力 | 说明 |
|---|---|---|
| B1 | 扫码进入 | 打开链接即用，不登录、不下载 App |
| B2 | 信息表单 | 昵称必填；单位、访客类型、分组、参观路线选填（字段以孙博模板为准） |
| B3 | 手写签名 | Canvas 手写，支持清空重签；允许跳过，只用昵称 |
| B4 | 提交与同步 | 提交后 1～2 秒内出现在大屏 |
| B5 | 电子身份牌 | Canvas 生成，含签名、昵称、单位、类型、分组、路线、二维码、有效期、学校标识；一键保存 PNG |
| B6 | 隐私说明 | 明示信息用途与保存方式，提供随时删除入口（对应学校"签名属隐私"的顾虑） |

### 2.2 交互
- 竖屏单列，两步完成：**填信息 + 签名 → 生成身份牌**
- 全流程控制在 30 秒内，字段尽量少，选填项可折叠
- 提交后在同一设备内允许修改自己的签名
- 保存身份牌：主动按钮保存；长按图片可作为兜底
- 表单校验只卡昵称，其余全部可留空

### 2.3 样式
- 与大屏共用同一套视觉语言，只做"被操作"的部分
- 签名区高度 ≥ 180px，笔迹 2.5～3px，触控目标 ≥ 44px
- 身份牌比例 750 × 1180，像"入校通行证"，适合截图保存和打印

## 3. 服务端与部署（已定：公网）

### 3.1 部署形态

| 端 | 形态 | 访问方式 |
|---|---|---|
| 大屏 | Windows 一体机 / 电视盒子，Edge 或 Chrome 全屏（kiosk） | 浏览器打开公网地址 |
| 手机 | 参观者自带手机 | 扫码打开同一公网地址（走移动网络，不连校园内网） |
| 服务端 | 阿里云轻量 4 核 8G（报价中已列 3,000 元/年） | 静态页面托管 + 实时通道同进程 |

### 3.2 服务端能力清单

| 编号 | 能力 | 说明 |
|---|---|---|
| C1 | 静态托管 | 大屏页、手机页、二维码页，同进程同端口，部署简单 |
| C2 | 实时通道 | WebSocket，签名 1 秒内广播到大屏；替代开发期的本机广播 |
| C3 | 数据存储 | 签到记录与签名图片落盘（SQLite 或文件），支持一键导出备份 |
| C4 | 在线统计 | WebSocket 连接数即真实在线人数，可区分大屏端与手机端 |
| C5 | 管理接口 | 口令保护的清空、导出、二维码地址配置（现场换地址不用改代码） |
| C6 | 运维兜底 | 断线自动重连、心跳保活、限流防刷、开机自启与进程守护 |

### 3.3 现场部署清单
- 一体机：Chrome/Edge 全屏 kiosk 模式，关闭屏保与休眠，断网自动重连
- 网络：大屏侧需能访问公网（有线或校园网出口），访客手机走自己的移动网络
- 地址：优先已备案域名 + HTTPS；来不及则 IP + 端口 + HTTP 应急
- 二维码：由服务端按当前访问地址动态生成，换地址不用重新出图

### 3.4 风险
- **ICP 备案周期**：大陆服务器绑域名需备案，通常数天到数周，11.9 前可能来不及 → 应急预案是用 IP + 端口 + HTTP
- **公网暴露**：签到页公开，需限流与口令保护的管理接口，防止刷屏和误清空
- **隐私**：签名图片一旦存到服务端，需明确保留期限与一键清除机制

## 4. 双端数据流（只定义接口，不落实现）

事件只有四种：`visit`（有人扫码进入）、`sign`（新增签名）、`presence`（在线心跳）、`clear`（清空）。

- `Store.list()` / `Store.add(rec)` / `Store.clear()` —— 读写签到记录
- `Bus.send(msg)` / `Bus.on(fn)` —— 双端实时推送

记录结构（草案）：
```
{ id, name, unit, type, group, route, sig, ts }
```
`sig` 为签名图片的 dataURL，缺省为 null（只用昵称的情况）。
